### [high] Re-parenting a task via PATCH parentId silently unassigns it outside assertCanAssign, with no message and no review re-sync

- Where: `app/api/tasks/[id]/route.ts:190` (assignment-bypass)
- What: When `patch.parentId` is set on a project task the route writes `data.assignee = { disconnect: true }` (lines 189-191) without calling assertCanAssign, without setting `reassignedTo`, and without any check on who the caller is beyond canAccessTask. The post-update hook at line 225 only fires `syncProjectReviews` when `patch.assigneeId !== undefined || patch.milestoneId !== undefined || patch.archived !== undefined` — `parentId` is not in that list. The moved task also keeps its old `milestoneId` (only children are re-pointed at line 200-202 when milestoneId changes, never the moved row itself), so a step can sit in a different milestone than its root.
- Impact: Any user who can merely SEE the project (e.g. a RESOURCE placed in the same department but not on the project) can strip the holder off any root task; the previous holder gets no notification, the task disappears from their Today, and they remain on the milestone's review-meeting attendee list because reviewAttendeeIds is never re-run. This is the only code path that writes assigneeId without going through lib/permissions.ts:67 assertCanAssign.
- Repro: 1. As a lead: POST /api/tasks {projectId:P, milestoneId:M, title:"A", assigneeId:X} → root task T1 held by X (X is auto-invited to M's review meeting). 2. As a RESOURCE in P's department who is NOT on P (visible via lib/project-visibility.ts:31): PATCH /api/tasks/T1 {"parentId": "<any other root task id in P>"} → 200. 3. GET /api/tasks/T1 → assigneeId null, milestoneId still M; GET /api/today as X no longer lists T1; the M review calendarEvent still has X as attendee; no Notification row was written for X.
- Verifier: Confirmed. app/api/tasks/[id]/route.ts:189-191 writes `data.assignee = { disconnect: true }` for any non-private task when patch.parentId is set; assertCanAssign is only called at line 109 under `patch.assigneeId !== undefined`, reassignedTo stays null so no message is sent, and the review-sync guard at line 225 lists only assigneeId/milestoneId/archived. The moved row's milestoneId is untouched (lines 200-202 only re-point children). The only gate is canAccessTask (line 78) -> visibleProjectIds, which includes every project in the caller's department (lib/project-visibility.ts:31), so a same-department RESOURCE not on the project can strip the holder. grep confirms this is the only assigneeId write outside assertCanAssign (tasks/route.ts:180 is gated; the other two are private-task nulls). Also reachable from the UI via drag in components/tree/tree-view.tsx:284,480,497.
